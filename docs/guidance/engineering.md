# Engineering guidance

Use these prompts when changing the system. Each answer points to focused guidance and executable
evidence rather than prescribing one technique for every workload.

## Concurrency decisions

| Ask                                               | Guidance                                                                                                                                                                       | Evidence                                                                                                                      |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Which invariant must survive concurrent requests? | Keep the stock check and update in one database transaction when reserving inventory. A read-modify-write sequence without coordination can lose updates.                      | [Transaction guidance](../architecture/transactions.md) and `npm run experiment:race-condition`                               |
| Are conflicts occasional or sustained?            | Prefer optimistic version checks with bounded retries for occasional conflicts. Prefer row locks when a hot record must serialize critical updates.                            | `npm run experiment:optimistic-lock`, `npm run experiment:pessimistic-lock`, and `packages/concurrency/tests/`                |
| What does order acceptance guarantee?             | The current HTTP path validates current stock and creates a `PENDING` order; it does not reserve inventory. Keep that boundary explicit until the atomic service is connected. | [Architecture overview](../architecture/overview.md) and `apps/api/src/create-order.js`                                       |
| How is the concurrency claim demonstrated?        | Use deterministic barriers and injected state so tests control the conflicting interleaving without timing sleeps.                                                             | `packages/concurrency/tests/unit/unsafe-inventory.test.js` and `packages/concurrency/tests/unit/optimistic-inventory.test.js` |

## Distributed-system decisions

| Ask                                           | Guidance                                                                                                                                                                                                | Evidence                                                                                                                                                 |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Can delivery repeat?                          | Design for at-least-once delivery: use a stable message identifier and commit the deduplication claim with the business effect. Do not describe transport delivery as exactly-once processing.          | [Messaging semantics](../architecture/messaging-semantics.md), [deduplication](../architecture/deduplication.md), and `npm run experiment:deduplication` |
| Which failures are safe to retry?             | Retry only classified transient failures for idempotent operations. Bound attempts, back off with jitter, dead-letter terminal work, and acknowledge only after success or durable dead-letter storage. | [Retry guidance](../architecture/retries.md) and `npm run experiment:retries`                                                                            |
| What happens when producers outrun consumers? | Bound queue depth and worker concurrency. Choose fail-fast rejection when callers can retry, or FIFO publisher waiting when delaying the producer is safe.                                              | [Backpressure guidance](../architecture/backpressure.md), `npm run experiment:backpressure`, and `npm run experiment:worker-pool`                        |
| What should a network partition sacrifice?    | Choose consistency or availability per operation and document reconciliation. Inventory reservations normally reject uncertain writes; stale catalog reads may remain available.                        | [CAP guidance](../architecture/cap.md) and `packages/concurrency/tests/unit/cap-partition.test.js`                                                       |
| How will data placement affect correctness?   | Account for replica lag, route read-after-write traffic deliberately, choose shard keys that avoid hotspots, and define leader expiry before failover.                                                  | [Replication](../architecture/replication.md), [sharding](../architecture/sharding.md), and [leader election](../architecture/leader-election.md)        |

## Fully local operation

| Ask                                      | Guidance                                                                                                                                                                                      | Evidence                                                                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Which services must run?                 | Start PostgreSQL and Redis with Docker Compose. Use the optional `app` profile only when testing the containerized API and loopback gateway.                                                  | [Local infrastructure](../../infra/docker/README.md) and `docker-compose.yml`                                             |
| What does the health endpoint prove?     | Treat `/health` as API-process liveness. Compose separately gates startup on migration and dependency health; focused integration tests prove database and Redis behavior.                    | `apps/api/src/app.js`, `docker-compose.yml`, and the integration test suites                                              |
| Which state survives a process restart?  | PostgreSQL and Redis use named local volumes. Queue messages, metrics, and in-memory experiment state do not survive their owning process.                                                    | [Observability](../architecture/observability.md) and [queue guidance](../architecture/queue.md)                          |
| How are failures investigated?           | Follow the correlation ID through structured API, message, and worker records, then inspect queue depth, retry, deduplication, conflict, and processing metrics.                              | [Observability](../architecture/observability.md) and its focused verification command                                    |
| Which local boundaries are illustrative? | Access policies are executable guidance but are not enforced by the runtime. Development credentials and the dedicated test database and Redis database must remain isolated from other data. | [Local access control](../architecture/local-access-control.md), [.env.example](../../.env.example), and `TEST_REDIS_URL` |
